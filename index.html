Bell Notification UI Enhancement

Wiom CSP App — Cross-Surface Attention Inbox (Attention Framework v1.3)

flag Objective

The Bell icon is a communication surface through which Wiom communicates important updates, actions, and alerts to CSPs. It brings together signals from different parts of the CSP journey — such as task failures, deduction warnings, quality drops, inventory alerts, and team messages — in one place.

Today, however, all notifications look almost identical. They are presented as plain text rows with only a read/unread indicator. As a result, when a CSP has 15+ notifications, they need to read each title to understand what requires their attention and why.

track_changes Goal

Improve the Bell experience so that a CSP can quickly scan and triage notifications within a few seconds, even before reading the text.

We want to introduce three key improvements:

1. Category-based icons
Use sourceClass to map each notification to a relevant visual icon, allowing CSPs to immediately distinguish between categories such as deductions, task failures, quality alerts, inventory, etc.
2. Read-state filters
Add filter chips — All / Unseen / Seen — so CSPs can quickly focus on the notifications that need their attention.
3. Clearer unread/read hierarchy
Create stronger visual differentiation between unread and read notifications, making priority and pending attention immediately apparent.
Core UX Principle

The Bell should not just be a notification list; it should act as a quick attention-management surface for CSPs.

The CSP should be able to look at the Bell and answer three questions almost instantly:
What happened? → What needs my attention? → Where should I act?

settings UAF — Bell Updates

1. Notification Expiry / TTL
Allow teams to define an expiry duration for each notification — either in hours/days or through an absolute expiry date. Once the TTL is reached, the notification should automatically expire/archive so that outdated notifications don't clutter the Bell inbox.
2. Notification Suppression / Deduplication
Prevent repetitive notifications from flooding the Bell inbox. If an unread notification with the same event type + group key already exists, UAF should either suppress the new notification or merge it into the existing notification by updating the groupedCount.
3. Notification Icon Selection
Allow teams to select an icon from a predefined icon library while creating/configuring a notification. The selected icon will be displayed alongside the notification to help CSPs quickly identify its category — for example, money, router, task/action, communication, etc.

data_object Notification Display & Retention Logic

timeline 1. Event Lifecycle (event_deadline)

Not all notifications age the same way. A deduction warning for "16 अक्टूबर" loses all relevance after October 16, while a policy update remains useful for weeks. To handle this, each notification can carry an optional event_deadline field.

  • ACTIVE event_deadline is in the future — the event hasn't happened yet. E.g. "16 अक्टूबर तक नेट-बॉक्स वापस करें" before Oct 16.
  • EXPIRED event_deadline has passed — the event already happened, the notification is no longer actionable. E.g. the same deduction warning after Oct 16.
  • TIMELESS No event_deadline — general info with no hard expiry. E.g. "नई पॉलिसी अपडेट", "₹150 कमीशन जमा हुआ".

grid_on 2. Visibility Matrix (Read-State × Event-Lifecycle)

Where a notification appears is decided by two axes: whether the CSP has seen it (read/unread) and whether the underlying event is still relevant (active/expired/timeless).

ACTIVE event_deadline in future EXPIRED event_deadline passed TIMELESS no deadline
Unread Initial load — always visible CSP hasn't seen it, event is upcoming. Highest priority. Shows with unread dot + bold title. Initial load — visible with "समय समाप्त" tag CSP hasn't seen it, but the event already happened. Still shows so CSP knows what occurred. Tagged as expired. Initial load — visible up to 30 days General unread notification. Stays visible on the initial screen up to 30 days from creation.
Read Initial load — visible CSP has seen it, event is still upcoming. Stays on initial screen as a reminder until the deadline passes. Show More only — dimmed + "समय समाप्त" tag CSP saw it, event has passed. Moves to the "show more" archive. No longer clutters the initial view. Retained for 30 days. Show More after 7 days — visible up to 30 days Recent read notifications (< 7 days) stay on initial load. Older than 7 days → moves to "show more" archive. Purged at 30 days.

account_tree 3. Display Flow

Step 1
App opens Bell
GET /bell returns all notifications. Server applies 30-day retention — nothing older than 30 days is returned.
→
Step 2
Initial Load
Client shows: all unread + read ACTIVE + recent read TIMELESS (< 7 days). Everything else held back.
→
Step 3
Show More
CSP taps "पुरानी सूचनाएं". Loads remaining notifications (read EXPIRED, older read TIMELESS) up to 30 days.
→
Step 4
30-Day Purge

visibility 4. Initial Load — What Shows on Screen Open

  • All unread notifications regardless of lifecycle — the CSP hasn't seen them yet
  • Unread + EXPIRED notifications get a समय समाप्त tag so the CSP knows the event passed, but still sees what happened
  • Read + ACTIVE notifications stay visible — the event is still upcoming, acts as a reminder
  • Read + TIMELESS < 7 days old — recent enough to be contextually useful
  • No number cap on initial load — server controls what's returned, client shows all qualifying items

expand_more 5. Show More (30-Day Archive)

  • Read + EXPIRED — event passed, CSP has seen it. Not on initial load but kept for reference
  • Read + TIMELESS > 7 days old — too old for the initial screen but within the 30-day window
  • Button label: पुरानी सूचनाएं (no duration shown in CTA)
  • Loads all remaining notifications in one batch (no pagination within "show more")
  • Expired notifications shown with समय समाप्त tag and dimmed opacity

delete_sweep 6. 30-Day Hard Purge

  • All notifications (read, unread, active, expired, timeless) older than 30 days are permanently deleted from the server
  • No client-side deletion — the server simply stops returning them
  • Footer label shows: पुरानी सूचनाएं स्वचालित रूप से हटा दी जाती हैं
  • The 30-day clock starts from createdAt, not from event_deadline

filter_alt 7. Filter Chips Behavior

  • सभी (All) — shows all notifications in current view (initial + show more if loaded)
  • नहीं देखें गए (Unseen) — shows only unread notifications. "Show more" button hidden (archive is mostly read items)
  • देखें गए (Seen) — shows only read notifications from current view
  • Counts update in real-time as CSP taps cards (mark-as-read)
  • Empty state shown when a filter has zero matching items

touch_app 8. Mark-as-Read on Tap

  • Tapping a notification card marks it read optimistically (instant UI update)
  • Fire-and-forget POST /bell/{id}/read — no loading state, no blocking
  • Visual changes on mark-read: unread dot removed, title weight drops to 500, icon tint dims to textHint
  • If on "Unseen" filter: card fades out after 300ms (moved to "Seen" list)
  • Header bell badge count decrements by 1
  • Read + EXPIRED notifications that were on initial load (because they were unread) stay in place — they don't jump to "show more" mid-session

schedule 9. Timestamp Display Format

Notifications show absolute date & time instead of relative strings ("2 मिनट पहले"). The client computes the display string from createdAt using the rules below.

Condition Format Example
Today — createdAt date == current date आज h:mm a आज 10:30 PM
Yesterday — createdAt date == current date − 1 कल h:mm a कल 11:20 PM
Older — createdAt date < current date − 1 dd/MM/yyyy, h:mm a 25/09/2026, 10:30 AM
  • Locale: 12-hour clock with AM/PM — matches the CSP's typical phone locale (Hindi/English)
  • Timezone: Device local timezone (TimeZone.getDefault()), not UTC
  • Date comparison: Compare calendar dates (not 24-hour windows) — a notification at 11:55 PM shows "कल" after midnight, not after 24 hours
  • No relative strings: Never show "2 मिनट पहले" or "12 दिन पहले" — absolute timestamps let CSPs judge recency without mental math
  • Kotlin format pattern: SimpleDateFormat("dd/MM/yyyy, h:mm a", Locale("en", "IN")) for older dates

checklist 10. Quick Decision Summary

Question Decision
How many notifications on initial load? No fixed cap. Server returns all qualifying items (unread + recent read). Client renders all.
How long are notifications kept? 30 days from createdAt. Server purges after 30 days.
When does "show more" appear? When there are older notifications (read EXPIRED or read TIMELESS > 7 days) not shown on initial load.
Do expired unread notifications disappear? No. They stay on initial load with a "समय समाप्त" tag so the CSP sees what happened.
Do read ACTIVE notifications move to "show more"? No. They stay on initial load as reminders until the event deadline passes.
Is "show more" paginated? No. Single batch load of all remaining notifications within 30 days.
Does marking read move the card during the session? No. Cards stay in place during the session. The sorting recalculates on next Bell open.
Who owns TTL / expiry logic? Server (UAF). Client only reads event_deadline to show the "समय समाप्त" tag.

Current Implementation (Code)

  • Flat list — no visual category per notification
  • No leading icon — only unread dot + text
  • No filter chips — all items shown always
  • Read/unread distinguished only by dot + bg tint
  • sourceClass exists in model but unused in UI
  • Every notification row looks identical

Enhanced Design (Target)

  • Leading icon per sourceClass in 40dp rounded container
  • Filter chips — All / Unseen / Seen with live counts
  • sourceClass drives icon selection (6-way mapping)
  • Monochrome icon tint from DS tokens (no new colors)
  • Stronger unread emphasis: dot + bold title + icon tint
  • Read items: dimmed icon tint + lighter title weight
Gap 1
No Visual Category
sourceClass (TASK_EVENT, SYSTEM_STATE, PROGRAM_STATE, etc.) is in the data model but the UI ignores it. Every notification renders as identical text rows.
Gap 2
No Leading Icon
Without icons, the CSP must read Hindi text to identify notification type. A router icon or chat bubble communicates the category instantly.
Gap 3
No Filtering
No way to view only unread or only seen items. CSPs with 20+ notifications must scroll through everything to find what they haven't acted on.
Gap 4
Weak Read/Unread Contrast
The only visual signal is a small 8dp dot and a background tint shift. Adding icon emphasis and title weight creates a stronger scannable hierarchy.
